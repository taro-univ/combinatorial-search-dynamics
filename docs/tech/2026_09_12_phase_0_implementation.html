2. Canonical JSONによる決定的ID

identifiers.pyは値をUTF-8のcanonical JSONへ変換し、SHA-256 digestの先頭24 hexadecimal文字、つまり96 bitを短い種別prefixと組み合わせる。Python組込みのhash()には、processごとのrandomizationがあるため使用しない。

PrefixID入力
ins_instance IDcanonicalな問題定義
trl_trial IDinstance ID、完全な実験条件、sampling seed
chk_checkpoint IDtrial ID、生成token位置
art_artifact ID安定した内容記述
exp_experiment ID人間可読名、実験条件

object keyはsortし、区切り文字から空白を除き、UnicodeはUTF-8のまま保持する。nested dict、list、finite floatを決定的に扱う。NaN、正負Infinity、非文字列object key、JSON化不能なobjectは、曖昧な変換をせず例外で拒否する。保存順やParquetの行番号はID生成に関与しない。

3. PyArrow schemaとversion境界

現行versionはSCHEMA_VERSION = "1"としてdata/schemas.pyだけで定義する。instances、trials、checkpoints、metricsのPyArrow schemaは、仕様書の列名、型、nullable、列順をそのまま固定し、先頭にnon-nullのschema_version列を加える。

Table主なキーnullable列
instancesinstance_iddifficulty_value
trialstrial_id、instance_id外部キーllm_revision、error_type
checkpointscheckpoint_id、trial_id外部キーstate_json、objective_value、optimality_gap、tensor_ref

Parquet schema metadataにはlogical_tableとschema_versionを保存し、timestampはtimestamp[us, UTC]とする。読込み時に列、型、nullable metadata、実値のnull、table metadata、versionを検査する。未知のtable名と未対応versionは専用の明確な例外で拒否し、暗黙のmigrationは行わない。

6. DuckDBを問合せ層に限定

DuckDBは永続データベースを正本にせず、検証済みParquetを直接読むin-memory viewとして使う。pathはSQL文字列へ手作業で埋め込まず、DuckDBのrelation APIへ渡す。

instances.instance_id = trials.instance_id
trials.trial_id       = checkpoints.trial_id

analysis_checkpointsは上記IDによるinner joinで、各checkpointに問題条件とtrial条件を付加する。instance、trial、checkpointそれぞれのschema versionは別名にし、列名衝突を避ける。同じinstanceに複数trialがあってもtrial IDを通じて正しく展開される。

metricsは同名の独立viewとして参照できるが、checkpointとの不自然な多対多joinを避けるため代表viewには含めない。4つのParquetのいずれかが欠ける場合は、欠損file名を示して失敗する。

2. 0-1ナップサックTaskと目的方向の一般化

instanceは正整数のweights・values、正のcapacity、item count、generation seed、task名とversionを持つ。同じseedとHydra設定から同じinstance内容とinstance_idを再生成する。capacityはweight合計より小さくし、既定生成で全itemが自動的に入る自明な問題を避ける。

要素定義防御的検査
State0/1選択vector、total weight/value、stepvector長、0/1、再計算した合計との一致
Actionitem indexのtoggle範囲外とcapacity超過の追加を拒否
Objective選択itemのtotal valueを最大化元stateを破壊せずfloatで返す
Terminal証明済みoptimal到達、またはstep上限参照値なしでoptimalと断定しない

Phase 2のdummyはHamming距離の最小化、knapsackは価値の最大化である。この差をgenerator内の条件分岐へ埋め込まず、Task Protocolへobjective_sense、is_better、objective_gap、参照値付きis_success、deserialize_stateを追加した。mock generatorのgreedy選択はTaskの比較規則を使うため、両方向で同じ実装を再利用できる。

3. OR-Tools CP-SAT参照solver

solver境界はimmutableなSolverResultで、OR-Tools固有型をpipelineへ漏らさない。状態はOPTIMAL、FEASIBLE、INFEASIBLE、MODEL_INVALID、UNKNOWN、ERRORへ正規化する。未知のsolver名はregistryで明確に失敗する。

maximize  Σ value[i] * x[i]
subject to Σ weight[i] * x[i] ≤ capacity
           x[i] ∈ {0, 1}

既定parameterはmax_time_seconds=5.0、num_search_workers=1、random_seed=3001、relative_gap_epsilon=1e-9である。single workerはpilotの再現性を優先する判断である。返却されたsolution vectorはTask adapterへ戻し、capacity、目的値、solverのObjectiveValueが一致することを独立に検査する。

値保存規則
best feasible value実行可能解が得られた場合に保存
best bound最大化問題の最適値に対する上界
optimal valuestatusがOPTIMALの場合だけ保存
timed out非最適statusと明示的な時間制限到達規則から判定
error削除せずERROR行と短いerror typeを保存

4. 参照解schema、gap、feasible check

reference_solutions.parquetはPhase 1の4必須tableを壊さない任意拡張tableである。schema versionは既存の1を維持し、logical table metadata、UTC timestamp、canonical JSONのsolution・parametersを保存する。Zstandard、atomic write、暗黙上書き拒否はPhase 1のParquet APIを再利用する。

reference_id = hash(instance_id, solver name/version, parameters, solve seed)
solver gap  = max(0, best_bound - best_feasible) / max(abs(best_feasible), epsilon)
checkpoint gap = max(0, optimal - current_value) / max(abs(optimal), epsilon)

solver gapはbest feasibleとboundの差、checkpoint gapは証明済みoptimal値と現在価値の差であり、意味を分離する。実行可能解がなければsolver gapはnull、optimalityが証明されなければcheckpoint gapもnullである。数値誤差で負になるgapは0へ切り上げる。

validationは参照ID、複合キー、instance外部キー、status・timeout・optimality proven・optimal valueの整合、solution feasibility、目的値再計算、bound方向を検査する。checkpointについてはstate vector、total weight/value、capacity、step、1 actionごとの遷移、目的値、gap、success終端を検査する。同じinstanceへ異なる参照条件が混在する曖昧なsnapshotも拒否する。
